# STEP 04 Oracle 26ai schema and migration design

## Target and source

Oracle AI Database 26ai Free is the sole persistent target. `bans_chatbot/db/oracle/V001__initial_schema.sql` creates the 17 tables in dependency order. `V002__indexes_guards_roles.sql` adds indexes, published-version guards, and the five fixed roles. `manifest.sha256` pins their source bytes. `apply.sql` refuses a nonempty schema, runs both migrations once, and checks table/role/valid-trigger counts. None of these files is loaded by Spring Boot startup, `test`, or `local-mock`.

Oracle's [CREATE TABLE reference](https://docs.oracle.com/en/database/oracle/oracle-database/26/sqlrf/CREATE-TABLE.html) documents numeric `GENERATED ALWAYS AS IDENTITY`, which uses a sequence generator, and the constraints used here. IDs are `NUMBER(19)` to fit Java `long`. Text content uses Oracle `CLOB`; business dates use `DATE` or `TIMESTAMP(6) WITH TIME ZONE`. Oracle's [constraint reference](https://docs.oracle.com/en/database/oracle/oracle-database/26/sqlrf/constraint.html) confirms row-local `CHECK` conditions and PK/UNIQUE/FK behavior. Its [CREATE INDEX reference](https://docs.oracle.com/en/database/oracle/oracle-database/26/sqlrf/CREATE-INDEX.html) describes conditional uniqueness through a function-based unique index, used for active document approval. No H2 syntax or alternate database profile was introduced.

Redgate's [Oracle support page](https://documentation.red-gate.com/flyway/reference/database-driver-reference/oracle-database) lists 26ai as verified and both Redgate/Open Source Oracle modules. Its [support matrix](https://documentation.red-gate.com/fd/supported-database-versions-143754067.html?force_isolation=true) describes foundational migrations and licensing changes, but this repository has no resolved Flyway version/module or 26ai server with which to validate the exact execution mode. STEP 04 therefore uses versioned Oracle SQL and an explicit SQLcl/SQL*Plus runner. Flyway adoption is a later, separately verified choice; no unsupported license or version assumption is encoded in the POM.

## Manual application, only after Oracle is available

1. Provision a **dedicated empty application schema** in Oracle 26ai Free and grant only the privileges needed for its own objects. Do not connect as `SYS` or `SYSTEM`. Check and back up any existing schema before applying; `verify_empty.sql` rejects every nonempty schema.
2. Connect interactively using SQLcl or SQL*Plus so a password is never placed in a script, repository, command argument, or log. From `bans_chatbot`, run `@db/oracle/apply.sql`. The runner uses `WHENEVER SQLERROR EXIT`, applies V001 then V002, and checks 17 tables, five roles, and two valid triggers.
3. Record the applied version names, `manifest.sha256` hashes, Oracle service/version, timestamp, and result in a local deployment record without credentials. Do not rerun a migration file after a partial failure. Oracle DDL commits implicitly; inspect the schema and resolve the failure manually in an isolated environment. No DROP/reset automation exists.
4. After applying, explicitly run `oracleIntegrationTest.cmd` with `ORACLE_JDBC_URL`, `ORACLE_DB_USER`, and `ORACLE_DB_PASSWORD`. An optional empty-schema migration test requires `ORACLE_EMPTY_SCHEMA_MIGRATION_TEST=YES` **before** first application and leaves the schema populated; use it only in a disposable, dedicated test schema. The normal integration command expects the schema to be applied already.

The scripts and preliminary integration tests were **not executed on Oracle in STEP 04** because Oracle 26ai Free is not installed. Static Java tests check names, references, checksums, prohibited fields, and runner ordering; they do not parse Oracle SQL or prove that its DDL succeeds.

## Constraints and authorization boundary

- `employee.employee_code` is unique. `employee.employment_status` and `employee_account.account_status` are separate: employment lifecycle and login eligibility. `session_version` allows later session invalidation. Account activation stores only a token hash.
- `employee_role` is the current per-employee assignment of one of five seeded `system_role` values. Reassignment after revocation updates the current row and emits audit metadata; it does not append role history here. The service must reload current status and roles, not trust stale session claims.
- A direct `chat_room` stores exactly two sorted employee IDs: `employee_low_id < employee_high_id`, plus a unique pair. `chat_message` has unique `(room_id, room_seq)` and `(sender_id, client_request_id)`; `chat_read_state` has composite PK `(room_id, employee_id)`. The service must verify that a sender/reader is one of the room's two employees, because an ordinary FK to `employee` cannot express that disjunction. Room sequence allocation and lock behavior require Oracle tests.
- `document.document_scope` is COMPANY, DEPARTMENT, or PRIVATE. A department-scoped document requires `department_id`; other scopes forbid it. Explicit employee READ/APPROVE grants live in `document_grant`, with revocation metadata. The service still checks account status, role, document ownership/scope, grant revocation, and current version. `DOCUMENT_MANAGER` plus an active APPROVE grant is required by the policy; an FK alone cannot enforce that cross-table rule.
- `document.current_version_id` is nullable during initial insert, then its composite FK `(document_id,current_version_id)` points to the same document's `document_version`. The order is: create document, create version, then select current version. A published version and its fragments are protected by Oracle triggers; a later edit creates a new version. `document_review` records reviewer, decision, and optional revocation; a function-based unique index permits at most one active approval per version. Document approval status and active review consistency still require a single service transaction and Oracle integration checks.
- `document_fragment.ai_searchable` and `external_ai_allowed` are independent flags. The latter may be `Y` only when synthetic and non-sensitive flags are also `Y`; it does **not** follow from search eligibility. External disclosure additionally requires an approved current document version, fresh RBAC+ACL, a matching fragment, trusted question review, and explicit feature activation. Those service checks are later work; no live Gemini client or AI transcript table exists here.
- `audit_event` stores event/outcome/resource/request metadata only. Its actor may be null for anonymous security events. It has no content, error detail, secret, question, or answer column.

The 17-table design has no extra migration-ledger table. The versioned filenames and SHA-256 manifest detect source drift offline; the empty-schema guard prevents rerunning the initial application. A durable migration history and repeatability under real Oracle remain open until a verified migration tool is selected. Index selectivity, storage, transaction behavior, constraint timing, rollback, and concurrency remain **BLOCKED: ORACLE_26AI_NOT_INSTALLED**.

## STEP 05 pre-application schema refinement and seed

Before any Oracle application, V001 was refined to hold `employee.company_email` (unique), `extension_no`, `duty_summary`, `document.document_code` (unique), and `document_category`. The version-state check now accepts `DISCARDED`. Stable business codes let a separate Oracle `MERGE` seed match rows without assuming generated identity values. The SHA-256 manifest was recomputed for this still-unapplied V001 revision; V002 and the 17-table structure are unchanged. If an older V001 has already been applied outside this documented workspace, do **not** rerun or overwrite it; plan a forward Oracle migration instead.

The synthetic seed lives under `db/oracle/seed`, outside migration version numbering. Its explicit `apply_seed.sql` uses `WHENEVER SQLERROR ... ROLLBACK`, preflight checks, exact-count verification, and a final `COMMIT`; the DML itself contains no commit. Twelve account rows use an unusable `!PENDING_ACTIVATION!` marker in the required hash column and remain `PENDING`. No usable password or activation token is committed. STEP 06 must issue random activation codes, store their hashes, and replace the marker with a real password hash before any account becomes active. See `docs/fixture-and-seed.md` for execution conditions. No Oracle seed execution or idempotence claim has been validated yet.

## STEP 06 unapplied account schema and Mapper boundary

V001 was refined again **before Oracle application**. `employee_account` now includes nonnegative `credentials_version` and `failed_login_count`, plus nullable `locked_until TIMESTAMP(6) WITH TIME ZONE`. The new V001 SHA-256 is `81473a778a8baba7888ecabd896377c55f63bb8724778450bd5800c3a9b0bbd6`; check the manifest before first application. The existing `session_version` remains in the schema; STEP 06 session invalidation compares the newly added credentials version and current employment/account state on each authenticated HTTP request.

The `auth` domain's Oracle MyBatis XML locks an account row with `FOR UPDATE OF a.password_hash` before activation-code issuance/consumption or login-failure changes. Activation consumes an unconsumed, unexpired hash and conditionally changes only a pending account with the expected credential version in one Spring transaction. Returning the login failure outcome from that transaction allows the failure counter/lock to commit before the public 401/429 is raised. This is a design and source-level result only: no Mapper statement, transaction, lock, timestamp conversion, or persistence was executed against Oracle 26ai in STEP 06. All remain **BLOCKED: ORACLE_26AI_NOT_INSTALLED**. The all-pending seed requires a separate safe first-admin bootstrap and code delivery procedure; no usable bootstrap secret is checked in.

## STEP 08 chat migration addition

`V003__chat_message_length_guard.sql` is now third in the explicit empty-schema `apply.sql` runner and SHA-256 manifest. It adds a CLOB length trigger for chat messages. `verify_schema.sql` now expects 17 tables, five roles and three valid triggers. Historical V001/V002 descriptions above refer to their earlier state; V003 has **not** run on Oracle. Before applying to any existing schema, review migration state and use a deliberate separate procedure; `apply.sql` deliberately rejects a nonempty schema. Real Oracle compile/Unicode behavior is **BLOCKED: ORACLE_26AI_NOT_INSTALLED**.

## STEP 10 V004 reviewer assignment

`V004__document_reviewer_assignment.sql` adds `document.review_assignee_id` and its employee FK. The explicit empty-schema runner applies V001–V004 in order; its SHA-256 manifest includes V004. This source has not been run on Oracle. No change was made to prior migration bytes. The column is cleared after approve/reject. A manager role and active READ+APPROVE grants are rechecked by the service inside the repository's document-row lock before decision. The existing immutable published version and fragment triggers stay in effect; an old published version remains the current pointer until a newly submitted draft is approved. Later ALTER application to an already-populated schema requires a separate reviewed operation; the existing runner rejects it.

## STEP 11 V005 search metadata

`V005__document_search_tags_indexes.sql` creates `document_tag` with a `(document_id,tag_value)` PK and document FK, plus tag and current-document B-tree indexes. The schema now expects 18 tables; `apply.sql`, `verify_schema.sql`, SHA-256 manifest, offline source checks and the explicit Oracle IT migration list include V005. The seed renderer produces one category tag per synthetic document, and seed preflight/verification require the table and 20 tags. The SQL uses bound `INSTR` and `DBMS_LOB.INSTR` over the current approved version with viewer account/role/department/live grant joins. CLOB substring search is not accelerated by these B-tree indexes; Oracle Text/Korean analyzer and execution plan remain unselected until verified on actual Oracle 26ai. Neither V005 nor the updated seed has been executed here. The runner still requires a dedicated empty schema; an already-populated schema needs a separately reviewed forward migration.
