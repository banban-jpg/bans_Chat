# Security policy — STEP 18 현재 정책

현재 보안 경계는 Spring Security 서버 세션과 현재 계정 재조회다. 초기 MVC interceptor는 trusted request actor를 소비하는 추가 검사로 통합됐으며 단독 인증 수단이 아니다. 아래 최신 정책이 우선하고 뒤의 STEP별 설명은 당시 이력이다.

- 익명 GET은 /, health 두 경로, CSRF API, 정확한 네 UI 자산이다. POST activate/login도 공개지만 CSRF가 필요하다. 나머지 요청은 활성 EMPLOYEE 세션이 필요하며 domain RBAC/ACL이 추가된다. 전체 /ui/**를 공개하지 않는다.
- ACCOUNT_ADMIN은 직원/코드 발급만 관리하며 문서 ACL 우회/자기 승인 권한이 없다. DOCUMENT_MANAGER만 배정 검토자+READ/APPROVE 조건에서 승인한다. 소유자 자기 승인은 거부한다. AUDITOR는 문서 우회나 아직 없는 감사 조회 UI를 의미하지 않는다.
- 세션 고정 방지, HttpOnly/SameSite 쿠키, 현재 credentials version/status/department 검사와 STOMP CONNECT CSRF/origin/user queue 제한을 유지한다. account/grant/department 변경을 캐시된 과거 권한으로 우회하지 않는다. 동시 final-check 이후 Oracle race는 미검증이다.
- AI는 검토된 가상 질문과 현재 승인/게시/외부 허용/합성/비민감 구간만 사용한다. 사용자 질문도 외부에 갈 수 있음을 명시한다. regex masking/클라이언트 synthetic 주장/모델 출력은 허가 근거가 아니다. AI 질문·초안·키를 DB/로그에 저장하지 않는다. API는 검증된 일시적인 사실/인용 DTO를 반환한다.
- 모든 UI 동적 출력은 textContent/허용 요소이며 HTML/Markdown 지시는 실행하지 않는다. CSRF/같은 origin/메뉴 외 서버 인가를 유지한다. 에러는 고정 code/message, STOMP conversion 예외는 CHAT_REQUEST_INVALID다. debug/wire/HTTP body/JDBC bind 로그는 비밀·질문·세션을 노출할 수 있어 켜지 않는다.
- local-mock은 127.0.0.1 기본/비영속이고 관리자 비밀번호는 실행 중 환경으로만 공급한다. oracle 쿠키는 Secure다. 운영 확장에는 TLS·인증서·내부망·방화벽/프록시 신뢰·계정 분리·비밀 교체·로그 접근/보관 정책이 필요하며 이번에 검증되지 않았다.
- Oracle 최초 관리자 bootstrap/실 DB 보안/백업 복구/외부 scanner/실 Gemini/실제 Chrome 클릭 검증은 완료되지 않았다. 검증 결과의 PASS/FAIL/SKIPPED/BLOCKED/NOT_RUN을 구분한다. Git 비밀 패턴 검사는 제한된 검사이며 전체 보안 인증이 아니다.

현재 기준과 공개 API는 [api-contract.md](api-contract.md), 실제 공격 case는 [security-test-results.md](security-test-results.md), 미검증 범위는 [known-limitations.md](known-limitations.md)를 따른다.

## 아래는 STEP 03 이후 정책 변화 이력

The server identity is an authenticated employee ID, department code, current account status, and a set of security roles. Job title is never a role. Client `userId`, document metadata, and model text are never authorities. Default decision is deny. `SUSPENDED` and `DEPARTED` accounts cannot use protected operations even if their session still carries roles; production authentication must refresh account status and revoke sessions after a status change.

Roles are `EMPLOYEE`, `ACCOUNT_ADMIN`, `DOCUMENT_EDITOR`, `DOCUMENT_MANAGER`, and `AUDITOR`. An active employee needs `EMPLOYEE` for ordinary protected access. `ACCOUNT_ADMIN` can manage another account but cannot grant a role to itself. `DOCUMENT_EDITOR` is an editing role, never approval authority. Approval requires `DOCUMENT_MANAGER`, document read access, and a resource-specific `APPROVE` grant. `AUDITOR` is for audit access; it grants no document read bypass. Administrator roles never bypass private document ACLs.

An approved company document can be read by active employees. An approved department document can be read by an active employee in that department, its owner, or an employee with a `READ` grant. A private document is readable only by its owner or a specifically granted employee. Drafts are readable only by their owner or a specifically granted employee. Search uses the same decision for every result. A direct conversation is readable only by its two active participants. A resource denial is presented as 404 where revealing existence would help enumeration; an anonymous request gets 401.

External AI transfer is a separate decision after document read authorization. Every proposed document **segment** must belong to that document, have `external_ai_allowed=true`, and be marked synthetic and non-sensitive by trusted server metadata; its document must be approved. The proposed question must pass a trusted server-side synthetic/non-sensitive review. Regex masking alone is not an approval. The question text can leave the server if a later real Gemini transport is explicitly enabled. There is no production review adapter or external transport in STEP 03, so no real transfer can be authorized or attempted.

Only exact `GET /health`, `GET /api/health`, `POST /api/auth/activation`, and `POST /api/auth/login` are anonymous. The last two routes are policy reservations and do not exist yet. An interim MVC session interceptor enforces this for current HTTP MVC requests; `/api/demo/employees` now requires a server session. It does not establish a login session or replace the required Spring Security server-session chain. No Spring Security dependency was added from an uncached artifact in this offline STEP. WebSocket, STOMP, static resource, and other non-MVC security must be wired and tested before those surfaces are exposed.

HTTP errors use the STEP 02 envelope. 401 `AUTH_REQUIRED` means no trusted session. 403 `FORBIDDEN` means an authenticated actor is inactive or a non-hidden operation is forbidden. 404 `NOT_FOUND` also hides a document or chat resource denied by ACL. 429 `RATE_LIMITED` is reserved for a future limiter. Public messages never contain internal exception reasons, secrets, document text, or AI questions. `X-Request-Id` is generated by the server.

`EmployeeRole` and `DocumentGrant` are Java models only. STEP 04 must define Oracle 26ai DDL, constraints, and MyBatis ACL queries. The current Mockito grants and fake session actors are not evidence of DB joins, instant revocation, or a production authentication flow.

## STEP 06 authentication update (2026-11-03)

The earlier STEP 03 route and interim-boundary statements above describe historical state. STEP 06 implements `POST /api/auth/activate` (not `/activation`), `/login`, `/logout`, `/me`, and `GET /api/auth/csrf`. Spring Security now owns the server-session and CSRF filter chain. Custom login explicitly saves the security context and changes the session ID. A trusted filter reloads active account status, roles, and credentials version on every authenticated HTTP request; a stale or ineligible account invalidates its session. The MVC interceptor still checks the trusted request attribute for current MVC endpoints.

Passwords use BCrypt. An account locks for 15 minutes after five failed attempts. Random activation codes are 256 bits, 24 hours by default, one-use, and stored as SHA-256 hashes; reissue invalidates the prior code. No code-issuance HTTP endpoint or delivery service exists yet. The seeded Oracle administrator remains pending until a safe first-admin bootstrap is defined. `local-mock` may use an operator-provided environment password for synthetic EMP-001, but its state is process-local and ephemeral. No WebSocket/STOMP authentication is implemented yet; those surfaces must not be exposed as protected production operations until wired to the same policy.

## STEP 13 read-only tool boundary

The prior sections describe earlier stages; implemented STEP 09 STOMP security and STEP 10–11 document workflow are in handoff.md. STEP 13 tools require the real Spring Security server session, current account/credentials/EMPLOYEE role and CSRF on preview POST. Tool calls never trust supplied callerId/role/department or a forged MVC actor. Read permissions are rechecked for every invocation and final Mock handoff. ACCOUNT_ADMIN is not a private/department document bypass.

Only exact server-reviewed synthetic example questions are accepted after a transfer acknowledgement. The UI and service explicitly state that question text may leave the server when real AI is enabled and prohibit actual business/personal/confidential input. Arbitrary text is denied rather than certified by masking. Five read-only tools have bounded schemas/results; no SQL, salary, credential, write, role or grant tool exists. Public directory results must match canonical synthetic records, and document excerpt export requires current approved publication/ACL plus trusted external/synthetic/non-sensitive flags, independent of internal read permission.

Tool payloads currently go only to Mock; the live provider rejects this contract. DTO projection excludes non-allowlisted fields and source titles, and model/document instructions cannot invoke another operation. Session counters and bounded audit hold metadata only; HTTP returns counts/notice only, not conversations. Final-check races, actual Oracle JOIN/flag/JDBC/audit transaction behavior remain BLOCKED pending 26ai. See ai-tool-security.md for executable limits and the distinct live activation boundary.

## STEP 14 question and evidence boundary

Question POST and examples/UI require current authenticated sessions; POST also requires CSRF. Actual account/session identity is refreshed, ignoring all body authority claims. Only exact server-reviewed synthetic questions are processed; unknown text (including potential PII/injections) is not sent to any model or echoed. The UI/service explicitly warn that question text itself can leave the server, ban actual business/personal/confidential input and offer reviewed choices. No regex or acknowledgement certifies arbitrary text.

Structured facts come from the six-field canonical public service projection with a final read. Document processing separates internal search from externalSource: current approved/PUBLISHED version, ACL/grants and all external/synthetic/non-sensitive flags are mandatory. At most one short excerpt and reviewed question may reach the separate grounded Provider contract, still behind explicit live activation. No tool payload is enabled for real Gemini. Strict exact S1/quote checking rejects invented facts, model URLs and policy instructions; final source/identity revalidation precedes the server answer. Missing/ambiguous/stale evidence yields a fixed non-disclosing UNANSWERABLE result.

The required approved answer DTO is transient, no-store, and rendered as text. It does not reflect the submitted question or raw model draft; no history/log/DB/browser-storage transcript is added. Audit includes only actor/model/type/outcome/count/latency. Safe AI errors and counters do not change chat authorization or REST/STOMP handlers. Existing final-check races, session/process limiter limits, blocking DB/audit I/O and Oracle audit durability remain unverified. See ai-question-orchestration.md and oracle-validation-backlog.md; no final security/operational certification is claimed.
